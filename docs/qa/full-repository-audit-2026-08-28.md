## Gaps found and fixed in this audit

1. **CI blind spot: 6 of 16 tracker JS files were never syntax-checked**, including this session's own new `operator-identity.js`. `.github/workflows/site-qa.yml` checked only 10 files. Added a new step covering `universal-proof-questions.js`, `human-labels.js`, `analytics-mobile-v2.js`, `call-outcomes.js`, `crm-manage.js`, `operator-identity.js`.
2. **`tests/call-outcomes.test.js` existed but was never wired into any CI workflow** (flagged already in `docs/qa/current-state-audit-2026-08-28.md`, item 9, but not fixed there). Added as a CI step; passes (4/4).
3. **The credential-leak scan in `site_qa.py` only ever covered `caawi/`**, never `tracker/` — meaning if the service-role key were ever accidentally pasted into any tracker script, nothing would have caught it. Extended the same forbidden-marker check to every file in `tracker/*.js`. Confirmed clean today.
4. **6 unindexed foreign keys**, all from this session's own operator-attribution columns (`family_leads.assigned_operator_id`, `family_leads.last_actor_id`, `family_interviews.operator_id`, `sales_opportunities.owner_operator_id`, `sales_activities.operator_id`, `ops_events.operator_id`), flagged by the Supabase performance advisor. Added covering indexes for all six.
5. **A duplicate index** on `family_contact_starts.request_id` (`family_contact_starts_request_id_key` and `..._uidx` were identical), flagged in the phase-1 audit and never cleaned up. Dropped the redundant one.
6. **Tracker accessibility**: `#password`, `#search`, `#status`, `#need`, `#city`, `#days` lacked accessible names; `#iUrgency`, `#iNextAction`, `#iFollow` had visible `<label>` text that wasn't programmatically associated (`for=` missing). Fixed with `aria-label` where no visible label exists and `for=`/`id` pairing where one already does — no visual change, verified against `usability_qa.py` before/after.
7. **An orphaned duplicate interview design**: `internal/first-call-questionnaires.md` is a free-text questionnaire (different field names, "5–10 minute" target) that predates the field-ID-based implementation and is read by no code anywhere in the repo. Marked historical at the top of the file rather than deleted, per the repo's own convention of routing rather than erasing stale material.

## Explained, not a bug

- **The single production `family_interviews` row's 31 answer keys match no field currently defined in code.** Traced to a real historical cause, not corruption: the interview's route-specific fields were rewritten (most likely around the 27 Aug instrument-design work) without preserving old field IDs, and that one row predates the rewrite. It is the only interview ever completed in production, so the practical impact is limited to that single row undercounting in any future field-level aggregate — it does not affect new interviews. `family_interviews.interview_schema_version` (added earlier this session) now gives future rewrites a way to be detected instead of silently breaking aggregates again, but nothing yet reads/enforces it — that is a "wire it up later" item, not urgent at n=1.
- **Analytics funnel math** (`family-leads-admin`'s `analytics` action): reviewed the full `makeJourneys`/flow/dropoff calculation. Journeys correctly dedupe repeated same-name events per session before counting; the "current form" funnel is correctly scoped to `CURRENT_FORM_VERSION` so old form versions can't silently distort today's conversion rates. No bugs found in this pass — this is a read-through, not a formal proof, and should not be taken as an exhaustive guarantee.
- **The double prompt (tracker password, then operator identity) the user flagged as friction is working as designed, not broken** — live data confirms the sign-in path actually completes and links a real account. It is a deliberate two-layer interim (per `docs/decisions/0002-two-operator-os-interview-and-data-foundation.md`) specifically so nothing broke while it rolled out. Collapsing it to one prompt is a real, bigger decision (replacing the shared password with the JWT as sole gate) that remains intentionally deferred, not silently fixed here.
- **"Does the system learn?" (`family_scenarios` / `scenario-learning.js`)** — the code path is real and correctly wired (`match_scenario` fires automatically after every completed interview via `tracker/scenario-learning.js`'s `sync()`, calling `family-scenario-admin`), but `family_scenarios` and `family_scenario_research` both still have 0 rows and the one completed interview's `scenario_fingerprint` is still null. So: **the learning mechanism exists and is correctly triggered, but has never actually captured anything in production** — this is an adoption gap (operators have never pasted a completed deep-research answer back into the "Save verified research to AQOON" box), not a code defect.
- **"Broken links" flagged by `check_verified_links.py`**: all 19 failures returned the identical `Tunnel connection failed: 403 Forbidden` error from this sandboxed session's own outbound network proxy, not from the target sites — this could not have been 19 unrelated government/employer sites failing at once with the same error. This check needs to run in the repo's own `verify-seo-links.yml` GitHub Action (unrestricted network) to be trusted; it could not be verified from this session.
